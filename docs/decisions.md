# 설계 결정 기록

결정마다 대안과 이유. 실행 중 바뀐 결정도 지우지 않고 남긴다.

| # | 결정 | 대안 | 이유 |
|---|---|---|---|
| 1 | 오케스트레이터 = Claude Code 메인 세션 + 스킬 | Python 오케스트레이터(`claude -p` 병렬 실행), API 기반 프레임워크 | API 키·추가 비용 없이 Pro 요금제 안에서 동작해야 함. 서브에이전트는 다른 서브에이전트를 부를 수 없으므로 지휘는 메인 세션이 맡는 구조가 자연스럽다. 대가: 지휘 규칙이 코드가 아니라 지침이라 매번 같은 순서를 보장하지 않는다 → 실행 시각·검사 결과를 로그로 남겨 사후 확인. |
| 2 | Figma는 MCP 대신 플러그인 ZIP 생성 | Figma MCP로 직접 읽기·수정 | 계정이 View 시트라 MCP 읽기 호출이 월 20회로 제한(Figma 공식 문서 확인). 기존 포트폴리오는 PDF로 읽고, 결과물은 기존에 쓰던 로컬 빌더로 ZIP을 만든다. |
| 3 | 경험 후보 에이전트를 "공고 무관 정리(indexer)"로 변경 | 공고를 보고 관련 경험을 고르는 screener를 공고 분석과 병렬로 실행 | 사용자 검토에서 "관련 경험 고르기는 공고 분석에 의존한다"는 지적. 병렬로 두면 분석을 건너뛴 거짓 병렬이 된다. 정리(공고 무관)와 판단(분석 후, 메인 세션)을 나눠 병렬을 정당하게 만들었다. |
| 4 | 저장소를 `job-portfolio-agent/` 하위 폴더에 둠 | 개인 PDF 50여 개가 있는 상위 폴더를 저장소로 쓰고 허용 목록 .gitignore | 맥락 없는 평가 에이전트가 ".gitignore 한 줄 실수가 곧 유출"이라고 지적. 개인 자료를 저장소 밖에 두면 구조적으로 커밋될 수 없다. |
| 5 | 포트폴리오는 Figma 보드의 행(경험 묶음)마다 대표 1개, 한 번 읽고 저장 | 전부 읽기 / 최신 2~3개만 / 매번 읽기 | 같은 행은 비슷한 경험 묶음이라 2개 이상 읽으면 중복. 다른 경험까지 보려면 행마다 하나씩. PDF 내용은 공고와 무관하게 고정이므로 반복해서 읽을 이유가 없다. |
| 6 | 코드 검사는 정답이 정해진 것만 (인용 존재, 제외 키워드, 수치 출처, 글자 수) | 기여 칸 채움 검사, PDF 인용 검사, 개인 파일 유출 pre-commit 등 | 사용자가 "의미 없이 복잡한 것"을 지적. 칸이 채워졌는지는 내용이 맞는지 알려 주지 않음. 저장소를 분리해 유출 위험이 .gitignore 한 줄로 줄었음. |
| 7 | 맥락 없는 평가 에이전트로 계획 검토 | 계획 작성자(나)가 스스로 검토 | 작성자는 자기 가정을 못 본다. 실제로 실행 전 발견: 기존 빌더가 `parents[1]/assets` 경로를 고정 → 계획대로 복사했으면 첫 빌드 실패. 지원 회사의 기존 문항 답변이 docx뿐이라 PDF 추출기로는 못 읽음. |
| 8 | 에이전트별 모델: 읽기·정리는 Haiku, 분석·작성·디자인은 Sonnet, 지휘는 Opus | 전부 같은 모델 | 가장 많이 읽는 곳에서 사용량을 아끼고, 정확성이 필요한 곳(인용, 글)에 더 강한 모델. 인용 정확성은 코드 검사가 뒤에서 받친다. Step 0에서 모델 지정이 동작함을 확인. |
